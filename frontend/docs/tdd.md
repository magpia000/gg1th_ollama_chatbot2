3단계 — 작업 처리 프롬프트 (TDD 기반)

tasks.md의 체크되지 않은 작업을 하나씩 순서대로 처리한다.

규칙:
1. 한 번에 하나의 하위 작업만 진행한다. 여러 작업을 동시에 처리하지 마라.
2. 작업 시작 전, 해당 작업에 필요한 React API/라이브러리 사용법을
   context7로 재확인하고 버전 불일치가 없는지 검증하라.
3. TDD 순서를 지켜라: 
   (1) 실패하는 테스트 작성 → (2) 최소 구현으로 테스트 통과 → (3) 리팩토링
4. 하나의 하위 작업이 끝나면 다음 하위 작업으로 자동으로 넘어가지 말고,
   결과를 요약해 보고한 뒤 내 승인을 기다려라.
5. 상위 작업에 속한 모든 하위 작업이 끝나면 해당 상위 작업의 체크박스를 체크하고
   여기서도 멈춰서 보고하라.
6. 설계도(chat_ui_설계도.jpg)와 실제 렌더링 결과가 다르다고 판단되면
   임의로 수정하지 말고 먼저 나에게 질문하라.

## 진행 현황 (실행 이력)

`docs/tasks.md`의 상위 작업 1~5(하위 작업 총 38개, 사용자 요청으로 추가된 3.6·5.7 포함) 전부 완료. 규칙 적용 과정에서의 주요 사항:

- **규칙 2(context7)**: 세션 내내 context7 MCP 도구가 연결되지 않아 사용할 수 없었다. 대신 react.dev 공식 문서를 직접 조회해 API/패턴을 검증했다(`frontend-prd.md` 각주 참고).
- **규칙 3(TDD)**: 대부분의 작업은 실패하는 테스트 → 최소 구현 → 리팩토링 순서를 그대로 따랐다(Vitest + @testing-library/react, 최초 도입 시 사용자 승인받음). 다만 `App.jsx`의 순수 state 선언(1.3)이나 아직 호출부가 없는 핸들러 정의(1.5, 1.6)처럼 그 자체로 관찰 가능한 동작이 없는 "뼈대" 작업은 진짜 red 단계를 만들 수 없어, 구현 후 회귀 테스트로 대체하고 그 사실을 매번 보고했다. CSS 브레이크포인트(반응형 레이아웃)는 jsdom이 실제 레이아웃을 계산하지 않아 유닛 테스트 대신 Puppeteer로 실제 브라우저(및 실제 백엔드)에서 검증했다.
- **규칙 4·5(단계별 보고/승인)**: 사용자가 명시적으로 "이어서 진행"을 지시한 구간(상위 작업 3~5 등)에서는 여러 하위 작업을 연속 처리하되, 상위 작업 경계나 중요한 발견(문서-코드 불일치 등)마다 멈춰서 보고했다.
- **규칙 6(설계도 vs 구현 차이)**: 구현 중 발견한 PRD/코드 불일치(예: `backend/schemas.py`의 실제 `model` 기본값이 PRD 서술과 다름, §3.3 "고정" 구조에 테스트 파일이 반영 안 됨)는 임의로 고치지 않고 먼저 질문해 승인받은 뒤 반영했다.
- **최종 사용자 검수 후 변경**: 최종 결과물 확인 후 두 차례 피드백을 받아 반영했다 — (1) 사이드바가 채팅 화면을 덮는 오버레이 방식을 레이아웃을 밀어내는 고정 패널 방식으로 변경, (2) 좌우 여백 확대, (3) assistant 응답에 사용 모델/응답 시간 메타 정보 표시 추가(FR-18). 세 건 모두 TDD로 진행하고 실제 브라우저에서 재확인했다.
